# JSON runtime baseline — 2026-11-17

Run: GitHub Actions `JSON runtime throughput benchmark` on Ubuntu 24.04.

Host: Intel Xeon 6975P-C, x86-64, 4 logical CPUs.

Workload: 100,000 requests per run, 7 timed runs, same 122-byte nested JSON
input per request. Each implementation parses, validates `id` and `workers`, and
compact-encodes the parsed document. Every run produced the same checksum
(17,000,000) and total input-plus-output bytes (24,400,000).

| Runtime | Median requests/s | Median MiB/s | Relative to Brew |
|---|---:|---:|---:|
| Goose 2026.4 | 3,123,620 | 726.86 | 1.31× |
| **Brew C11 JSON runtime** | **2,375,199** | **552.70** | **1.00×** |
| Rust + serde_json | 929,343 | 216.25 | 0.39× |
| Go + encoding/json | 536,714 | 124.89 | 0.22× |

Brew measured 76.5% of Goose throughput, 2.57× Rust, and 4.45× Go in this
specific parse/compact workload.

## Measurement boundary

This is an in-process JSON runtime benchmark, not an HTTP/network benchmark.
Brew dispatches through its x86-64 C ABI to the C11 JSON runtime driver; the
repeated hot loop runs in that runtime helper. The result therefore measures
Brew's native runtime path, not Brew loop overhead or per-request FFI overhead.
Go uses `encoding/json`; Goose uses its standard-library JSON DOM/writer; Rust
uses `serde_json` with insertion-order preservation. Seven timed runs rotate
execution order. Reported throughput percentiles are run-level samples, not
per-request latency percentiles.

The full raw JSON and Markdown report are attached to the successful workflow
run artifact `json-runtime-benchmark`.
