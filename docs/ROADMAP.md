# Swan Performance Engineering

## Current architecture

Swan emits x86-64 System V assembly directly from its semantically checked AST. The compiler does not use LLVM, Clang, or C source generation. The C11 frontend and code generator are intentionally small; the system assembler and linker are used only to assemble and link emitted assembly.

## Implemented compile-time optimizations

- Arena-backed AST storage.
- Compact token records and shared token-text storage.
- Lazy AST call-argument allocation.
- Hash-indexed function, semantic-symbol, and backend-local lookup.
- Cached call-presence metadata.
- Low-overhead literal assembly emission and checked output-buffer growth.
- Direct process spawning instead of a shell pipeline.
- Source-level standard-library imports with duplicate suppression.

## Implemented runtime optimizations

- Register-backed locals with callee-saved and caller-saved register use plus stack spills.
- Caller-saved register preservation around user calls, libc calls, and output.
- Direct local-to-local arithmetic and comparisons.
- Constant folding and single-return leaf-function inlining.
- Short-circuit logical operators.
- Power-of-two signed division lowering.
- A proven-nonnegative midpoint pattern that uses an unsigned shift instead of signed-division correction.
- Direct addressing for register-resident array bases.
- Loop strength reduction and guarded loop transformations.
- Optional unchecked `u32` arrays for code where bounds are independently proven.

## Benchmark methodology

The checked-in binary-search comparison uses:
- 20,000,000 contiguous `u32` elements.
- 20,000,000 queries generated by the same modular recurrence.
- Identical target sequence and checksum across implementations.
- Five interleaved runtime samples per implementation.
- Separate compile time, compile peak RSS, runtime, runtime peak RSS, and executable size.
- Swan checked and unchecked array variants, Goose, Rust, C, and C++.

The one-billion-element sorting workload is separate and intentionally excluded from normal CI.

## Measurements

Performance numbers are recorded by GitHub Actions artifacts. Results must be compared only when the workload, machine, compiler options, and source revision match. Shared-runner noise can materially affect timings; use the five-sample median and avoid drawing conclusions from a single run.

## Next hot paths

1. Liveness-aware register allocation and call-site-specific preservation.
2. Range-check elimination for safe array indexing.
3. Common-subexpression and copy propagation across basic blocks.
4. A typed low-level IR with basic blocks and explicit memory operations.
5. Better constant division lowering and strength reduction for arbitrary divisors.
6. Instruction scheduling and target-aware register pressure control.

Every optimization must have correctness coverage and a reproducible benchmark delta before being described as a speed improvement.
